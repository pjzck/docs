# 打包更新进度条"来回打架"：从日志口径到 UDP 协议重设计

> 来源：2026-09 Lucky 打包版更新器（launcher 侧 `pub/tools/scripts/launcher/packed_app.lua`、CI 侧 `Source/base/tools/aur/ci/utils/index.lua`）。
> 本文只沉淀**可复用的结论与坑**：一个"进度来回跳"的问题怎么定案、怎么改、修完怎么验。标「实测」的是本机真跑过的；标「推断」的没验。

## 1. 先把问题定义清楚

| 项 | 内容 |
|---|---|
| 期望 | 更新期间进度条单调前进，不因上报先后回退 |
| 实际 | 进度在 ~30% ↔ 100% 之间来回跳（"打架"），整段时间反复清零重爬 |
| 触发条件 | 打包版更新分"下载 → 解包"两阶段，解包阶段有 N 个 worker 并发拷文件（实测该阶段 930 个 ≥4MB 文件同时在拷） |
| 修复判据 | ① 相位内聚合值单调不回退 ② 相位切换只清一次 ③ 收尾能到 100% |

结论先行：**进度条不是"渲染抖动"，是上报口径打架**——同一时刻有两套步号、两种分母在交替进门，而接收端把"步号变化"当成了"清零重来"。

## 2. 上报链路与三个必须知道的事实

链路：CI 子进程（主线程 + N 个 worker 线程）→ UDP 127.0.0.1 → launcher 汇总 → 进度条。

**事实一：`p` 就是"输出字节比例"，可以直接当字节用。**「实测」
`ks.disk_file_copy(src, dst, cb)` 的回调是 `p = (copy_sz - 剩余) / copy_sz`（`ks/vfs/vfs.c:405`），`copy_sz` 取自 `ks_vfile_stat(src).size`（`kslua/vfs_lua.c:881/899`）；zip 源的 stat 返回**原始（解压后）大小**（`ks/vfs/vzip_file.c:306/485`），而拷贝循环按解压后的字节计数。
→ 所以 `size * p` 就是该文件已落盘字节，**下载与解包两个阶段同口径**，不需要再用 stat 去还原压缩比。回调粒度是 64KB~1MB 一块，也就是增量的最小粒度。

**事实二：跨线程传对象是"入队时刻的快照"。**「实测」
`KSTQueue:push` 会 **pickle 深拷贝**（`kslua/thread_lua.c:319`）。把进度对象当参数发给 worker，worker 手里那份是**派发那一刻的快照**——若"统计总量"发生在派发之后，worker 报出去的分母就是**部分值**。

**事实三：日志步号是 DFS 嵌套编号，不是相位标识。**「实测」
CI 侧 `Step X.Y: ... 已开始/已完成` 的编号随嵌套变化（`1`、`1.1`、`1.2`，父步骤还在栈上时子步骤是它的下一层）。若主线程与 worker 各自持有不同的 progress 对象，同一时刻会报出 `1.1`（主）与 `1`（worker）两套编号；更糟的是子阶段会改写共用的模块级 `progress_step_` 且不恢复。

## 3. 为什么"来回打架"：三个可独立致跳的机制

| # | 机制 | 现象 |
|---|---|---|
| M1 | 接收端**步号一变就清零**，并且把"画面值高水位 `shown`"一起清零 | 唯一保证不回退的东西被自己抹掉，任何一次误判换步 = 可见地倒回 0 |
| M2 | 两个上报者的**步号 + 分母都不同**（主线程报过期步号 `1.1` + 全量分母，worker 报 `1` + 部分快照分母），而换步判定只看步号字符串 | 相邻两个包就换一次"步"，**每个包清一次零**；分母还忽大忽小，比值被 clamp 到 1.0 再掉回来 |
| M3 | 两个口径**相加**（主进程"已完成字节" + worker"在拷文件字节"）且用高水位兜底 | 文件完成瞬间它同时出现在两侧 → 重复计数；高水位把这个虚高**永久留下**（"卡 100%"同源问题） |

一句话：**高水位与平滑只能修饰"单调的输入"，救不了"会误清零、会重复计数"的输入。**

## 4. 旁路探针：最便宜的真机取证

改造前的判断都是静态读码，最快的定案方式是在**接收端**插一支只读探针（不改任何进度状态）：

- **每包原始字段与聚合后口径同屏打印**：`step / total / done / file / cur` + `聚合{total done inflight(N个) agg shown}`；
- **换步必报**（节流 50ms）+ **定时采样**（500ms）+ **每个 step 的收包计数**——三个合起来就能看出"是不是两个上报者在交替"；
- **落盘**：内存保留最近 N 行（ring buffer），每次用整文件覆写落盘（若运行环境只有 `disk_file_save`、没有 append），既避免刷爆 UI 面板，又能事后统计；
- **放在被测函数末尾**、只读、且被上层 `trace_pcall` 包住：即使探针自己抛错也污染不到进度状态与退出状态。

产出的判据很机械：**换步累计次数**、**出现过的 step 值个数**、**出现过的 total 值个数**、**agg 回退次数**、**shown 是否超过 agg**。

## 5. 真机数据（修复后，54.5GB 的一次解包）

「实测」探针输出统计（同一 launcher 会话内还残留了一轮 590MB 小更新的尾巴，可作对照）：

| 指标 | 结果 | 含义 |
|---|---|---|
| 出现过的 step 值 | **只有 `1`** | 主线程与 worker 步号一致，M2 的输入前提消失 |
| 换步累计 | **1** | 整个大相位没有发生"换步" |
| 大相位 total | **恒为 54,551,042,519** | 分母唯一且稳定 |
| agg 样本 | 94 个，0.000 → **0.993**，回退 **1** 次 | 唯一那次回退发生在第 4 行：total 从 590MB 换成 54.5GB，即**新一轮/新相位的起点**，属正常 |
| shown 回退次数 | **0** | 画面值不回退 |
| shown 是否超过 agg | **0 次** | 平滑只从下方逼近，不超调 |
| 收尾兜底 | `done` 停在 36.7GB 时，`Σ每文件` 从 49.0GB 涨到 50.4GB，agg 随之 0.965→0.993 | "取大不相加"的兜底口径确实在工作 |
| 规模 | 4685 个包 / 930 个文件条目 | 包速率与条目量级（评估 UDP 缓冲与单帧收包上限用） |

## 6. 重设计的协议（v2）

**载荷**：`{phase, step, total, done?, file?, cur?, name?}`——全部是**每文件绝对字节**，不是增量。

| 发送方 | 字段 | 何时 |
|---|---|---|
| 主进程 | `done` = 累计完成字节；`file`/`cur` = 刚完成文件及其大小 | 相位开始（分母包，`done=0` 且不带 file）+ 每个文件完成时 |
| 每个 worker | `cur` = `size * p`（该文件绝对已拷）、`file` = **最终目标路径**、`name` = 显示名 | 拷贝回调，节流 100ms，**最后一块必报** |

**接收端规则**（可照抄）：

- **分母只认相位开始包**，并且**必须在派发 worker 之前发出**——顺带把"统计总量"前置到派发之前，worker 快照里的分母自然就是完整值（M2 从构造上消失）。
- **重置键是 `phase`（单调递增整数），不是内容字段**：`phase` 变大才清 `received_bytes`、per-file 表、`shown`、`finished_bytes_seen`；**worker 包永远不触发清零**。
- **聚合取大不相加**：`max(主进程累计完成量, Σ每文件高水位)`。两条口径是同一个总量的两个下界，取大即可互相补漏且不会重复计入。
- **per-file 条目在相位内不删除**（它参与求和），UI 列表另用"完成事件"驱动收敛。
- **显示层只做单向平滑**（例：150ms 内逼近实收值），并且**不得越过实收值**——平滑是显示修饰，不是兜底。
- **完成信号双保险**：结构化上报之外，保留"当前相位已完成"的文本信号，用于补偿**最后一个 UDP 包丢失**的场景。
- **每次更新重开 socket**，隔离上一轮残留的 UDP 包。
- **文件标识用最终目标路径**（不是临时路径），避免"改名"造成同一文件两个 key 而重复计数。

## 7. 可复用检查清单

1. 进度数值**只有一个写者**（结构化上报）；日志/文本只写文案，数值与文案分家。
2. 清零/重置只由**单一权威信号**（单调相位号）驱动，且不由上报内容推断先后。
3. 分母一次相位只认一个，且在**派发并发任务之前**确定。
4. 抗丢包：要么每包带**绝对锚点**（按文件或按总量取高水位），要么有**独立完成信号**兜底；**纯增量累加丢一包就永久短斤少两**，必须另配锚点。
5. 多个口径**只能取大，不能相加**（相加的两个口径一旦语义重叠，就会重复计数）。
6. 高水位/平滑属于显示层，**不能用来掩盖输入的非单调**。
7. 跨线程传递对象默认是**值快照**（pickle），需要"实时视图"就必须换成显式上报或共享句柄。

## 8. 遗留观察（尚未处理）

- **两个面板共用同名全局表**：App 更新面板与 Server 更新面板各自的 `progress_inflight_` / `progress_file_names_` 都是**裸全局**（`packed_app.lua:162-163`、`packed_server.lua:167-168`），而两者被同一个界面模块 import 进同一个 lua_State → socket 隔离了，**表没隔离**。两个更新同时进行时，聚合会把对方的文件算进来、列表也会混显。
- **在拷列表没有过期兜底**：per-file 条目有意不删，但"显示名"只在收到完成包时移除；该包丢一次，名字会挂到相位结束。
- **解包阶段的显示名传的是绝对路径**，下载阶段传的是相对名 → 解包时列表行会很长。
- 「推断」若把"每文件高水位"换成"每文件 stat 高水位"，也能覆盖"回调停滞"这类丢失，代价是每帧触碰文件系统，并且要处理临时文件改名后 stat 取不到的时间窗；本次落地方案选择了"主进程累计完成量"作锚点，未使用 stat。
